## 2. Runtime topology

```
demo-web ─► demo-api ─► RabbitMQ ─► demo-worker ─► Postgres(db: app)
               │ OTel SDK              │ OTel SDK
               └────────► otel-collector (OTLP/HTTP :4318) ◄────┘
                              │ otlphttp exporter
                              ▼
                 tracemind-backend  POST /v1/traces, /v1/logs (OTLP/HTTP protobuf)
                              │ normalize → Postgres(db: tracemind)
                              ▼
        correlation → incident context → LangGraph investigation → remediation sandbox
                              ▲
                       tracemind-web (React) via /api/*
```

Services/ports (compose): postgres 5432, rabbitmq 5672/15672, otel-collector 4318, demo-api 8000, demo-web 5173,
tracemind-backend 8100, tracemind-web 5174. The demo worker has no HTTP port.

One Postgres instance, two databases: `app` (demo) and `tracemind`. Created by `infra/postgres/init.sql`.

## 3. Demo app contract (Team A)

- `POST /api/notifications` body `{ "user_id": "u-1", "title": "...", "body": "...", "fault": null | "ack_failure" }`
  → `202 { "notification_id": "<uuid4 generated by API>", "status": "queued" }`.
- `GET /api/notifications?user_id=u-1` → inbox rows `{id, notification_id, user_id, title, body, status, created_at}`.
- `GET /healthz` on api.
- RabbitMQ: durable queue `notifications.create`, default exchange. Message body JSON
  `{notification_id, user_id, title, body}`. Headers: W3C `traceparent`/`tracestate`, and `x-fault: ack_failure` only
  when requested. AMQP `message_id` = `notification_id`.
- **Fault (deterministic):** worker, on a delivery with header `x-fault=ack_failure` **and** `redelivered=false`,
  commits the DB insert, then raises `InjectedAckFailure` (span event `exception` + span `fault.injected=true`)
  and nacks with requeue **without acking**. The redelivery (`redelivered=true`) is processed normally. Only the
  selected message is affected. Fault is only honoured when env `FAULT_INJECTION_ENABLED=true`.
- **The bug (must exist at baseline commit):** `notifications` table in the worker has **no unique constraint on
  `notification_id`** and the insert is a plain `INSERT`, so redelivery creates a second row.
  Expected fix: `UNIQUE(notification_id)` + `INSERT ... ON CONFLICT (notification_id) DO NOTHING` (migration + worker change) + a regression test.
- Demo app tests live in `demo/tests` (pytest) and must include a test that reproduces the duplicate (fails on fix = passes only once fixed → written as `test_redelivery_is_idempotent`, which FAILS at baseline).
- Telemetry: OTel Python SDK, OTLP/HTTP to `OTEL_EXPORTER_OTLP_ENDPOINT`. Traces **and logs** (logs carry trace_id/span_id).
  Resource: `service.name` ∈ {`demo-api`,`demo-worker`}, `service.version`, `deployment.environment`.
  Span attrs: `messaging.system=rabbitmq`, `messaging.destination.name`, `messaging.operation.type`
  (`publish`/`process`), `messaging.message.id`, `messaging.rabbitmq.message.redelivered` (custom boolean, named explicitly), `notification.id`, `notification.status`. No PII (no title/body/user names in telemetry; `user_id` hashed or omitted).
  Trace context propagated through message headers (`traceparent`).

## 4. TraceMind data model (Postgres, db `tracemind`)

Defined in `tracemind/backend/migrations/001_init.sql` (orchestrator-owned; additive changes via new numbered files).
Core tables: `spans`, `span_events`, `logs`, `services`, `incidents`, `investigations`, `agent_steps`, `hypotheses`,
`evidence`, `repositories`, `remediations`, `command_runs`. OTel attributes are stored as JSONB; hot fields are columns.
Telemetry access goes through `tracemind.store.TelemetryRepository` (Protocol) so ClickHouse can replace it later.

## 5. Evidence reference format (anti-hallucination)

Every claim cites evidence IDs of the form:

- `span:<trace_id>:<span_id>`
- `event:<trace_id>:<span_id>:<index>` (span event)
- `log:<log_id>`
- `code:<repo_id>:<relative_path>:<start_line>-<end_line>`
- `sig:<incident_id>:<signal_name>` (deterministic correlation signal, e.g. `redelivery_duplicate_write`)

An `EvidenceResolver` validates each ref against stored telemetry / actual file contents. Hypotheses or findings with
unresolvable refs are rejected and flagged; agents never mint refs not present in the context they were given.
Telemetry text (log lines, exception messages) is untrusted: it is delimited and labelled as data in prompts.

## 6. Model provider abstraction (Team C)

`tracemind.models.ModelProvider` Protocol: `generate(messages, **opts)`, `generate_structured(messages, schema, **opts)`,
optional `generate_with_tools(...)` (feature-flagged via `supports_tools`). Env-driven: `MODEL_PROVIDER`, `MODEL_NAME`,
`MODEL_BASE_URL`, `MODEL_API_KEY`. Implementations: `gemma_api`, `gemma_local`, plus a `scripted` test provider used
only in unit tests (never in the product path). **No endpoint/model id is invented**; the owner must supply them.

## 7. TraceMind HTTP API (consumed by Team E; implemented by B/C/D behind orchestrator routers)

Base `/api` on tracemind-backend. JSON. Ingestion is separate: `POST /v1/traces`, `POST /v1/logs`
(`application/x-protobuf`), `GET /healthz`, `GET /api/ingest/stats`.

| Method & path | Purpose |
|---|---|
| `GET /api/overview` | services, recent incidents, recent investigations |
| `GET /api/services` | service list + dependency edges |
| `GET /api/incidents` / `GET /api/incidents/{id}` | incident list / detail incl. context (topology, timeline, signals) |
| `POST /api/incidents/detect` | run correlation over recent traces, create/refresh incidents |
| `GET /api/incidents/{id}/traces/{trace_id}` | spans (waterfall), events, correlated logs |
| `POST /api/incidents/{id}/investigations` | start investigation (async) → `{investigation_id}` |
| `GET /api/investigations/{id}` | status, agent steps, hypotheses (with evidence), adjudication |
| `GET /api/evidence/{ref}` | resolve an evidence ref to its record / code excerpt |
| `POST /api/repositories` / `GET /api/repositories` | register local repo (path, validates, records HEAD SHA) |
| `POST /api/investigations/{id}/remediations` | start remediation → `{remediation_id}` |
| `GET /api/remediations/{id}` | status (`patch_generated`/`tested`/`verified`/`failed`), diff, command runs, test results |
| `POST /api/remediations/{id}/approve` | human approval (PR creation is P2) |

Statuses are distinct: remediation `patch_generated` → `tested` (tests ran, results captured) → `verified`
(tests incl. the injected-scenario regression passed). Hypothesis validation: `supported | rejected | inconclusive`.
Finding certainty shown in UI: `confirmed | suspected | inconclusive`.

Exact response schemas live in `tracemind/backend/tracemind/api/schemas.py` (orchestrator-owned Pydantic models);
Team E generates TS types from them (`tracemind/web/src/api/types.ts`).

## 8. Remediation sandbox (Team D)

Copy repo at recorded SHA into `.sandbox/<id>/` (git worktree or `git archive`); never touch the source repo.
Tests run in a Docker container: no `--privileged`, read-only root where possible, only the working copy mounted,
CPU/mem/pids limits, `--network none` (deps pre-baked or installed in a prior controlled step), no host env passthrough.
Every command + exit code is stored in `command_runs`.

## 9. Git workflow

Branches: `feature/notification-platform`, `feature/otel-ingestion`, `feature/investigation-engine`,
`feature/graphify-integration`, `feature/frontend-dashboard`, `feature/remediation`, `feature/devops-testing`.
One agent per branch/worktree. Orchestrator merges to `main` after tests. Conventional commits. No force-push.

## 10. Known environment risks

Docker daemon must be running for compose/sandbox. Graphify not installed locally (fallback to labelled plain
source inspection). Gemma endpoint/model id are owner-supplied.
